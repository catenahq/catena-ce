# Catena Keycloak extension

One JAR, `catena-keycloak.jar`, compiled against the Keycloak version in `pom.xml` (`keycloak.version`, which follows `keycloak_image_tag` in `catena-ce/ansible/reconcile/roles/keycloak/defaults/main.yml`) on Java 21. It holds three providers.

- `catena-tier-refusal`: an authenticator that refuses a sign-in like Keycloak's Deny access step, unless the user is a direct member of a top-level group named in the comma list in the signing-in client's attribute `catena.access.groups`, which admits the sign-in (a group of that name under another group does not count). Its factory names the reference category `catena-tier`, outside the ones the brute-force guard counts (`password`, `otp`, `recovery-authn-codes`), so a refusal on tier does not lock the account. It takes no configuration and offers the requirements REQUIRED and DISABLED.
- `catena-tier-binding`: a global admin-event listener. When an identity provider is created or updated, including by Partial import, and names no post-broker-login flow, it names the flow whose alias the realm attribute `catenaPostBrokerLoginFlow` holds, keeping the provider's organization links; a realm without the attribute, or whose attribute names no flow, is left alone. The server option `--spi-events-listener--catena-tier-binding--exempt-client=<clientId>` names a client of the admin realm whose updates are left alone. After the server's migration, the same binding runs over every realm holding the flow.
- `catena-client-email-code`: a sign-in step that asks for an email address and signs in the client who types the 6-digit code mailed to it. It needs no user and takes no configuration. Keycloak offers it, before anyone is identified, as an alternative to the username and password form (Try Another Way). The address post only records the address and queues a job on a one-thread queue the factory owns (100 jobs, extra ones dropped), so it never reads an account and answers every address with the same page, status and timing. The job, in its own transaction, looks the address up and calls Phase Two's `MagicLink.sendOtpEmail` only for an enabled person's account (no service account) with an email, outside the staff and administrator tiers, holding no role of the realm-management client, in a realm that holds both tier roles and an outgoing mail host. A code post compares in constant time and looks the account up only when the code matches; a wrong, expired or refused code, a locked or unknown account all give one invalid-code answer through a failure challenge, which counts toward the lockout of the account the address names (reference category `otp`). The failure is counted against the address the code was sent to, whatever the password form wrote to the attempted-username note since, and the fifth wrong post drops the code. The account is always resolved from that address; when the flow already holds a user (a re-authentication), the address post uses that user's email and a code for any other account is refused. A new code waits 30 seconds after the last one and a sign-in allows 5. The step never creates an account. Its page `catena-email-code.ftl` and its texts (English and French, including the select page labels) ship in the JAR's `theme-resources`.

All providers register through `src/main/resources/META-INF/services`.

## Build and test

Maven resolves Keycloak and Phase Two's `keycloak-magic-link` (the version the Phase Two image tagged `keycloak_image_tag` carries, used for its mail sender) as `provided` dependencies, so the JAR carries only this code.

    mvn -B -ntp --strict-checksums verify

runs the JUnit 5 and Mockito tests under `src/test/java` and writes `target/catena-keycloak.jar`. The build is reproducible: `project.build.outputTimestamp` is fixed, so two builds give the same SHA-256. The CI job `keycloak-provider` builds twice and compares.
